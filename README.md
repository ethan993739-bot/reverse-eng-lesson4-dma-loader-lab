## 二、本课背景：卡在“第一截”

分析这类加载器时，大家经常会卡在一个点上——**底层组件起来了，但往上还有好几截没接上**。
以本样本为例，它大致可以拆成下面这几层：

1. 用户态入口 → 登录 / 选项界面（UI 层）
2. 服务控制链：`OpenSCManager` → `CreateService` / `DeleteService` → `StartService`（服务层）
3. 驱动在内核拉起、服务进入 RUNNING（内核层）
4. 按选项加载对应的**加密资源包**（资源/配置层）
5. 资源包解密后，建立内核/DMA 通信通道（通道层）
6. 通过通道读写目标进程内存（执行层）

大多数人只走到第 3 层就停了，于是会得出一个片面的结论：“驱动起来了 = 成功了”。
但第 4、5、6 层才是真正把“选项”变成“能力”的部分。本课的任务，就是把这几截也补上。

---

## 三、学习目标

1. 还原样本从 UI 到驱动再到资源包与通信通道的完整调用链。
2. 弄清每个选项对应的是**同一份内核**，还是各自独立的模块——用证据说话。
3. 分析那类**加密资源包**的格式、解密方式与作用，搞明白它和选项之间的对应关系。
4. 定位用户态是如何打开通信口的，为什么“服务 RUNNING”不等于“可以通信”。
5. 区分「实验室环境里的验证效果」和「完整链路真实生效」之间的差距。
6. 用修改样本 + 观察行为变化的方式，验证你对整条链路的理解。

---

## 四、分析任务

围绕样本，完成以下工作（方法与工具自选，以能自圆其说为准）：

1. **链路测绘**：把样本启动后从点击操作到驱动加载、再到后续动作的完整调用链画出来，
   标注每一层的入口函数与衔接点。
2. **服务链还原**：弄清服务控制链的完整顺序（建/删/起），确认不同选项是否指向同一份内核。
3. **资源包分析**：找到选项对应的资源包，分析它的格式、加密/校验方式、解密与传递去向。
4. **通信口定位**：找出用户态是如何尝试打开通信口的，为什么该通信口可能不存在，
   以及后续哪些步骤会依赖它。
5. **能力边界判断**：说明样本在当前条件下能走到哪一层、哪些环节是空槽或未接通。
6. **动手验证**：对样本做局部修改，观察行为变化，验证你对某一层或某几层的判断。

## 五、可参考的排查方向（仅供参考，不必照搬）

- 先用信息收集摸清样本的字符串、节区、导入函数与相关关键词。
- 动态观察服务控制链的每一个 API 调用，记录参数与返回值。
- 对比不同选项下的行为差异，判断它们背后是“同一份内核”还是“多份模块”。
- 针对那类加密资源包，推断其结构与解密入口，尝试还原传递链路。
- 检查用户态对通信口的打开行为，结合内核对象命名判断“服务在跑”与“通信可用”之间的距离。
- 明确区分“实验环境里能验证的效果”与“完整链路真实生效”，避免把局部结论当全貌。
